## 1. Recommendation

**Build an independent, agent-agnostic verifier for AI-authored code changes.**
Working name: **Parinama Verify** (CLI: `pkv`).

Given a git diff produced by *any* AI agent (Claude Code, Codex, Cursor, Copilot, Aider…) or by a human, it:

1. Works out **which tests are affected** by the changed code.
2. **Actually runs them** in a sandboxed subprocess and records the exact command, exit code, timestamps, and the git tree hash.
3. **Detects test tampering**: deleted tests, removed or weakened assertions, newly added `skip`/`xfail`, expected values edited in the same change as the code under test, changed `conftest.py`/fixtures, and production files changed outside the stated scope.
4. **Detects stale evidence**: if the code changed *after* the tests ran, the "tests pass" claim is marked invalid.
5. Emits an **evidence report** (Markdown + JSON) generated by the tool, not by a language model. It can run as a pre-commit hook, a CLI, or a GitHub Action.

Initial scope: **Python + pytest repositories on GitHub**. That is one language, one test runner, and one CI system.

> **In plain words.** AI coding assistants now write a lot of code. A recurring public complaint is that they *say* "all tests pass" when that isn't true: the tests weren't run, were run on old code, or the AI quietly changed the tests so they would pass. That is like a student marking their own exam. Our first product is the **independent exam invigilator**. It doesn't write code at all. It checks the AI's work, runs the right tests for real, catches tampering, and gives you a receipt you can trust. It needs no expensive AI model to run, so it costs us almost nothing per user. That matters when we start with ₹0.

## 2. Public evidence

### 2.1 Developers distrust AI output; "almost right" is the main pain [F, via secondary reports of the survey]
- Stack Overflow 2025 Developer Survey (results post, 29 Dec 2025): adoption rose to ~84%, but **46% do not trust the accuracy of AI output**, up from 31%. "Almost right, but not quite" is the top frustration. Figures differ slightly across outlets (45% vs 66% for that item), so **check the primary report before quoting exact numbers.** [stackoverflow.blog](https://stackoverflow.blog/2025/12/29/developers-remain-willing-but-reluctant-to-use-ai-the-2025-developer-survey-results-are-here/), [InfoWorld](https://infoworld.com/article/4031673/ai-use-among-software-developers-grows-but-trust-remains-an-issue-stack-overflow-survey.html)
- METR RCT (Feb–Jun 2025): 16 experienced open-source developers, 246 real tasks. Tasks were **~19% slower with AI allowed**, while developers *believed* they were ~20% faster. METR notes the result is setting-specific and used early-2025 tools. [InfoWorld coverage](https://www.infoworld.com/article/4020931/ai-coding-tools-can-slow-down-seasoned-developers-by-19.html). *Primary METR paper not re-fetched this session.*

### 2.3 What already exists (competition) [F unless marked]
| Product | What it covers | What it does not cover (per its docs) |
|---|---|---|
| pytest-testmon / pytest-impacted / pytest-impact (OSS) | affected-test selection (coverage-based, or git-diff + AST) | tampering detection, evidence reports, staleness |
| CloudBees Smart Tests (ex-Launchable), GA Apr 2026 | predictive test selection for CI; pitched at "AI-generated code" | public pricing not found; tamper detection not advertised |
| Datadog Test Impact Analysis | coverage-based test skipping (.NET and Java in the docs seen) | Python not seen in the docs read; cannot detect library-dependency changes |
| GitHub Actions *Agentic Workflows* (preview), Copilot "explain/fix failure" | CI failure diagnosis inside GitHub | generated by models, i.e. not independent |
| Claude Code / Codex harnesses | could add native verification summaries (see #101247) | **main platform risk**: vendors may build this themselves |
| LLM PR reviewers (CodeRabbit, Greptile, Cursor Bugbot…) | model-generated review comments | *not verified this session*; model-generated, so not independent evidence |

> **In plain words: why this gap is real but narrow.** Tools exist that pick which tests to run, and tools exist where an AI reviews code. What I could not find is a tool whose *whole job* is to be a neutral referee between "the AI says it's done" and "it's actually done". It would catch the specific tricks: stale results, edited tests, skipped tests. The risk is that the big AI companies add this to their own products. Our defence is to work with *every* AI tool, run in the customer's own CI where the AI can't influence it, and be first and best at this narrow job.

## 4. MVP specification (stage 1–3 of the directive, reshaped)

```
pkv check [--base origin/main] [--run] [--json out.json] [--md out.md]
```
1. **Diff model:** `git diff --name-status` and hunks between base and HEAD, plus the working tree.
2. **Affected tests v0:** a static import graph (Python `ast`) from changed modules to test modules, plus tests in changed test files. Option: use the pytest-testmon database when present.
3. **Run:** `python -m pytest <selected> -q -p no:cacheprovider` in a subprocess with a timeout, a minimal environment (no secrets), and the network off where the OS allows. Record the command, exit code, durations, pytest summary, and the tree hash before and after.
4. **Tamper detectors v0 (AST diff of test files):** test functions removed; assert count decreased; `pytest.skip`/`xfail`/`skipif`/`unittest.skip` added; `assert True`/tautologies; an expected literal changed in a test while the code under test changed in the same diff; `conftest.py` changed; prod files in sensitive paths changed (`auth`, `security`, configurable).
5. **Staleness:** evidence is valid only if `tree_hash_at_run == current tree_hash`.
6. **Report:** a verdict ∈ {VERIFIED, UNVERIFIED, SUSPICIOUS}, with every claim backed by recorded data.
7. **GitHub Action:** comment the report on PRs, with a configurable fail threshold.

**Security:** the CLI never sends code anywhere and makes no LLM calls in v0. Repository content is treated as untrusted (we never execute anything except the test command the user configured).

**Validation without interviews:** a public repo and PyPI package; download and install counts; GitHub Marketplace installs; opt-in, anonymous, aggregate telemetry (verdict counts only, off by default); public issues; a published benchmark of tamper detection on synthetic, permissively licensed examples; later, a paid team dashboard offer to measure real payment.

**Revenue path [H]:** free OSS CLI → paid hosted history/dashboard for teams → private deployment for enterprises → a verification API that agent vendors can call. Prices are to be set only after a competitor price check, and treated as experiments.

**Link to research:** each run produces a trace (diff → import graph → selected tests → outcome). These traces are the natural data for EXP-005: do "change-impact analysis" primitives emerge from such traces, and do they transfer across repositories?

> **In plain words: what we build first.** A small command-line program that you run after an AI has changed your code. In about a minute it tells you: "these 14 tests are the ones your change could break; I ran them; 13 passed and 1 failed; also, the AI deleted 2 assertions in `test_login.py`. Here's the proof." It is free and open source, which earns trust and users. Teams that want history, dashboards and enforcement across many projects would pay. Every run also teaches us how engineers trace the effects of a change, which is exactly the kind of reusable "building block" our research studies.
